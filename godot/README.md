# godot/ — 이관 작업방

아직 게임이 아니다. **JS판을 답안지로 쓰는 방법이 진짜 되는지** 확인한 자리다.

## 지금 있는 것

| | |
|---|---|
| `project.godot` | 빈 프로젝트 (Godot 4.7) |
| `rules/num.gd` | sim.js의 `fmt()`를 옮긴 것 — 옮긴 첫 조각 |
| `tests/crosscheck.gd` | 같은 입력을 GDScript로 통과시킨다 |

## 돌리는 법

```sh
tools/godot-install.sh     # 이 작업방에 Godot을 깐다 (일회용 상자라 세션마다)
tools/crosscheck.sh        # JS판과 대조 → "✅ 5004개 전부 일치"
```

## 왜 이렇게 하는가

엔진을 옮길 때 제일 무서운 건 **조용히 달라지는 것**이다. 반올림 방향 하나만
어긋나도 몇 시간 뒤에 경제가 벌어지는데, 그때는 어디서 갈라졌는지 못 찾는다.

JS판(`sim.js`)은 몇 달간 실제로 돌아갔고 `tools/balance.mjs`로 수백 시간을
재본 코드다. 그러니 정답으로 취급할 수 있다. 옮긴 조각마다 같은 입력을
양쪽에 넣고 대조하면, 어긋난 그 순간에 잡힌다.

**첫 조각부터 실제로 걸렸다.** 옮긴 함수가 딱 하나였는데도:

```
입력 5625 · JS 5.63K · Godot 5.62K
```

JS의 `toFixed()`는 절반을 올리고(5.625→5.63), C의 `%.2f`는 짝수 쪽으로
붙인다(→5.62). 코드는 한 줄 한 줄 그대로 옮겨 적은 것이었다. 눈으로는
백 번을 봐도 못 찾는다.

고친 방법은 한쪽을 흉내 내는 게 아니라 **두 언어가 똑같이 할 수 있는 규칙으로
바꾼 것**이다 — 자릿수만큼 곱해 내리고 나누면 찍는 단계에 반올림할 게 안 남는다.

그리고 시험 문제를 고쳤다. 처음엔 난수만 뿌렸더니 한 번은 통과하고 다음엔
실패했다 — 반올림이 갈리는 건 값이 딱 절반에 떨어질 때뿐이라 우연히 걸려야만
드러났기 때문이다. **어쩌다 잡히는 시험은 시험이 아니다.** 지금은 씨앗을
고정하고 절반에 떨어지는 값을 일부러 전부 넣어 5,004개를 돌린다.
